### Changed
- 2026-10-09: **Recipe detail aligned with the "Chi tiết công thức" design boards** (web, mobile)
  - **Web**: the header shows the dish photo (`imageUrl`) in a rarity-glow frame beside the title, with a rarity-tinted bowl when there is none; facts are stacked label/value ("Tổng thời gian", "3 giờ"). Step cards put photos before the note; the note is a boxed "Lưu ý:" callout; the timer button reads "Bắt đầu hẹn giờ · 10:00" plus the step's timer label.
  - **Web list count**: with a filter on, the subtitle reads "N công thức phù hợp với bộ lọc" instead of claiming the filtered count is the whole library ("trong thư viện của bạn"). The API still returns no total.
  - **Mobile**: step photos are a horizontal 128×92 strip, the note is the boxed "Lưu ý:" callout under them, and the timer chip shows the icon and time only. Step extras moved to `recipe_step_extras.dart`.
- 2026-10-09: **Recipe form aligned with the "Thêm công thức" design boards; steps get a note** (backend, web, mobile)
  - **Step note**: each step has an optional `note` (tip or warning, max 500 chars) next to `name` and `text`. Stored in the steps JSONB (no migration), omitted when blank, shown under the instructions on the recipe detail (web and mobile). Regenerated the OpenAPI contract, web types and the Dart client; the mobile Drift step JSON carries it too.
  - **Save / Cancel always visible**: web pins "Hủy" and "Lưu công thức" in a bar at the bottom of the viewport while the form scrolls under it; mobile's fixed bottom bar now has "Hủy" next to "Lưu công thức" and the header has a close button.
  - **Web layout**: back link, large title, two columns (Thông tin chung, Nguyên liệu, Cách làm | Ảnh món, Thẻ) as section cards; servings stepper and a 1–5 difficulty slider ("3 · Vừa") on one row, compact ingredient rows with icon delete, step cards with a numbered badge, "Lưu ý" field, photo tiles, a "Thêm hẹn giờ" toggle and icon move/delete buttons. The title field is now labelled "Tên món".
  - **Mobile layout**: servings stepper, a 1–5 difficulty slider in a box ("3 · Vừa") on its own row, sections in the design order (tags last), step cards with the numbered badge beside the fields, "Lưu ý" field and timer toggle.
  - Not taken from the design: the "Độ hiếm dự kiến" preview (rarity is computed by the backend only), cover-photo upload (the recipe photo stays a URL), the 5-minute time stepper on mobile (time stays a typed number) and mobile's separate step / ingredient editor screens.
- 2026-10-08: **AI recipe import limited to one per user per minute** (backend, web, mobile)
  - **Backend**: `POST /parser/jobs` claims a per-user cooldown in Redis (`SET NX PX`, key `parser:cooldown:{userId}`, `PARSER_COOLDOWN_SECONDS`, default 60, 0 = off) after validation and the daily-quota check, so a rejected request does not cost the minute and concurrent requests cannot both pass. The created job carries `cooldownSeconds` (the configured length), and while the cooldown runs the API answers 429 `{code: "parse_cooldown", retryAfterSeconds}` with a matching `Retry-After` header; the daily-quota 429 has `code: "parse_daily_quota"`. Both bodies are in the OpenAPI contract (`ParseRateLimitError`). The minute is given back if the job could not be created or queued; a Redis outage answers 503. It replaces the old in-memory 15-per-minute throttle (`@nestjs/throttler` and `UserThrottlerGuard` removed); `GET /parser/jobs/:id` polling is unlimited.
  - **Web**: the import form disables its buttons and shows a countdown after a job starts, using the server's `cooldownSeconds` (or `retryAfterSeconds` after a 429, which shows only the countdown, no error line). The end time is kept in localStorage (a reload does not reset it) and cleared on sign-out.
  - **Mobile**: the import screen disables all three buttons and shows the countdown from the same server values (in memory; after an app restart the server's 429 restores it), even if the screen was left while the request was in flight, and clears it on sign-out.
- 2026-10-07: **Recipe ingredients and steps reworked** (backend, web, mobile)
  - **Optional amounts**: an ingredient line no longer needs a quantity or a unit ("muối, tùy khẩu vị"). A unit is only stored together with a quantity (clients drop it otherwise; the API answers 400).
  - **Vietnamese units, stored in both languages**: new `units` table (`code`, `name_vi`, `name_en`, `kind`, `to_base`) seeded by `pnpm db:seed` (g, kg, lạng, ml, lít, thìa cafe, thìa canh, cái, quả, củ, tép, nhánh, cây, lá, lát, miếng, con, bó, gói, hộp, nhúm, nắm). `GET /units` serves the catalog; the UI shows `nameVi` for now. Recipe lines keep the unit exactly as chosen instead of being converted to g / ml / piece. Thìa cafe / thìa canh are 5 ml / 15 ml (the old table used the US 4.93 / 14.79 ml).
  - **Grocery still sums in one unit**: each recipe line also returns `base` ({quantity, unit: g | ml | piece}), derived on read by the `units` module from the line's unit, the ingredient's default unit and density. Web and mobile aggregate `base`; lines without an amount or with an unsummable unit ("nhúm", "nắm") contribute 0 and show as a bare name. Counts such as quả / củ / nhánh all sum as pieces, so the list shows "6" rather than "6 nhánh".
  - **Portion scaling** rounds by unit code: g / ml to 5 (0.5 below 5), kg / l to 0.1, every other unit to 0.5 (shared vectors extended).
  - **Steps**: each step has an optional `name` (heading) and the `text` (content), plus up to 10 photos. Photos upload straight to object storage (`POST /media/uploads` with `purpose: "recipe-step"`, keys `recipes/{userId}/…`); a recipe can only reference keys under its owner's prefix. Responses carry `images: [{key, url}]` — `url` is `S3_PUBLIC_URL/key` when that is set, otherwise a 7-day signed GET URL.
  - **Parser**: drafts keep the source's own unit when the catalog has it (`2 tbsp` → 2 thìa canh) and convert only what it lacks (cup → ml, lb / oz → g); an unknown unit or unreadable amount leaves quantity and unit empty with the wording in the note.
  - **Migration `0003_recipe-units-and-step-details`**: creates `units`, makes `recipe_ingredients.quantity` / `unit` nullable with a foreign key to `units.code`, and turns stored `piece` units into "no unit". Run `pnpm db:migrate && pnpm db:seed`. Existing steps need no migration (name and images are optional in the JSONB). Mobile Drift schema v3 converts local rows the same way and adds a `units` cache that is pulled on sync.
  - Moved `prepare-image-upload` to `web/src/lib/images` and shared the signed-PUT upload (`uploadImage`) between the parser and step photos; mobile shares it as `MediaUploader`. The dart-dio generation script now strips enum/array defaults at any depth.
  - Tests: backend 190 unit + 40 e2e; web 161; mobile 191.
  - **Photo lifecycle**: a photo is deleted from storage when a step stops using it or its recipe is deleted (best effort, kept if another recipe of the same owner still references the key). Photos uploaded in a form that is never saved stay in the bucket. Uploads answer 503 when no S3 credentials are set; web and mobile show "Máy chủ chưa bật tính năng tải ảnh." instead of a connection error. With only S3 credentials configured everything works (signed URLs); `S3_PUBLIC_URL` is optional.
  - **Review fixes**: migration `0004` (and the Drift v3 upgrade) turn legacy "0 g" lines from unknown units into note-only lines; signed photo URLs last 7 days and mobile re-fetches recipes that carry signed photos on every sync; the web form blocks saving while a photo uploads; `update` locks the recipe row while computing which photos to delete; per-key `DeleteObjects` errors are logged; a saved unit stays visible on web while the catalog loads; mobile uploads photos in parallel (`step_photo_uploader.dart`) and only keeps `displayQuantity` for text Dart cannot parse, so plain numbers scale offline.
  - **Mobile upgrade**: queued offline edits that still carry free-text units are rewritten during the v3 migration (the wording moves into the ingredient note) so the server does not reject them.

- 2026-10-07: **Phase 06 — Smart Utilities** (implementation complete; on-device notification check outstanding)
  - **Shared vectors**: `docs/fixtures/{portion-scaling,grocery-aggregation,timer-math}-cases.json`; the same cases pass in the TS and Dart implementations of `scaleIngredientQuantity` / `roundForUnit`, `aggregateGrocery` and the timer math.
  - **Portion resizer**: servings stepper on recipe detail (web and mobile) scales ingredients live; g/ml round to 5 (0.5 below 5), pieces to 0.5, base servings are shown untouched.
  - **Grocery list**: "Thêm vào đi chợ" from recipe detail; `/grocery` (web) and Grocery screen (mobile) merge the same ingredient across recipes, group by aisle, tick items off, change servings, remove a recipe, untick all, clear the list, and share as text. Only `{recipeId, servings}` and ticked keys are persisted (IndexedDB / Drift); the aggregate is derived.
  - **Multi-timer**: start from a recipe step (prefilled) or ad hoc, run several at once, pause / resume / +1 phút / cancel. Timers store an absolute `endsAt` and survive reloads and restarts. Web: one ticker in a Web Worker, Notification API, synthesized chime, vibration. Mobile: one `Stream.periodic` ticker, a zoned `flutter_local_notifications` notification per timer (re-armed on launch; inexact fallback plus an in-app banner when Android denies exact alarms), floating dock via a `ShellRoute`.
  - **Mobile platform setup**: Android manifest permissions and receivers for scheduled notifications, monochrome `ic_stat_timer` icon, iOS notification delegate; Drift schema v2 adds `grocery_selections`, `grocery_checks`, `timer_entries`. New deps: `dexie` (+ `fake-indexeddb` for tests) on web, `share_plus` and `timezone` on mobile.
  - Review fixes: mobile sign-out cancels pending timer notifications; web session expiry (401) now wipes local grocery/timers like the sign-out button; mobile in-app alert rings again after +1 phút/resume (keyed on timer id + endsAt); grocery entries follow a recipe from its `local-…` id to the server id and are dropped when the recipe is deleted (locally or on the server); web no longer chimes for timers that ended long ago and tags notifications by timer id.
  - Tests: web 138; mobile 165; `flutter analyze`, `pnpm lint`/`typecheck` clean; web production build and Android debug APK build.
  - **Not verified**: notifications firing after the app is killed (needs a device or emulator run), iOS build, and the dock layout on very narrow phones. Building the Android APK on this machine needs `kotlin.incremental=false` in `android/gradle.properties` (Kotlin incremental caches fail across the C:/E: drives for `image_picker_android`); this was not committed.
- 2026-10-07: **Phase 05 — AI Recipe Parser** (implementation complete; live LLM verification and the 30-source eval outstanding)
  - **Backend**: `POST /parser/jobs` (URL or uploaded image key) and `GET /parser/jobs/:id`; BullMQ `recipe-parse` queue with a standalone worker (`pnpm worker:dev` / `worker:prod`, entry `src/worker.ts`). Pipeline: SSRF-safe fetch → `schema.org/Recipe` JSON-LD (free path) → otherwise Readability + Claude tool call (`save_recipe`, forced) → Zod validation → deterministic unit normalization → ingredient and tag matching against the catalog. Photos go to the vision model.
  - **SSRF protection**: http(s) on ports 80/443 only, no credentials, DNS answers must be globally routable (checked inside the connection's own lookup, so DNS rebinding cannot swap the address), every redirect hop re-validated, 5 MB cap applied after decompression, 10 s total timeout.
  - **Cost and abuse controls**: extractor output cached in Redis for 7 days by URL hash (versioned key; draft rebuilt against the current catalog), 30 imports per user per rolling 24 h (`PARSER_DAILY_QUOTA`, HTTP 429), one job creation per user per minute (`PARSER_COOLDOWN_SECONDS`, HTTP 429). The model only has the one extraction tool, so prompt injection in page text cannot trigger actions.
  - **Media**: `POST /media/uploads` returns a presigned PUT (S3/R2) whose signature pins content type and length; keys are namespaced `parser/{userId}/…` and a job can only read its owner's uploads. Upload limit is 5 MB (Claude's own image limit) rather than the 10 MB first planned; clients downscale to 2000 px.
  - **Web**: `/recipes/import` (link or photo → progress → draft opens in the regular recipe form), client-side photo downscale, one-click "add new ingredients to catalog".
  - **Mobile**: import screen (link, camera, gallery) opened from the list header; draft opens in the recipe form; same one-tap catalog add. `image_picker` added; iOS camera/photo usage strings added.
  - **Dev infra**: `docker-compose.yml` gains an S3-compatible `s3` service (SeaweedFS, `localhost:9000`) and an `s3-init` job that creates the bucket and browser CORS rule. Android emulator needs `adb reverse tcp:9000 tcp:9000` so the signed URL resolves.
  - **Tooling**: `pnpm parser:eval` (live eval against `eval/sources.json`, not in CI); OpenAPI, web and Dart clients regenerated.
  - Tests: backend 188 unit + 11 parser/media e2e; web 74; mobile 86. Verified manually: JSON-LD import of a real blog through the web UI, and a browser-originated photo upload to storage. **Not verified**: any real Claude call (no API key in this environment), the ≥85 % success target, mobile on a device.
  - Known limits: sites that block bots (e.g. 403) fail with `fetch_failed`; the planned "paste text" fallback is not built (needs a `text` source type and migration).
